Canonical status values are exactly DRAFT, AI_GENERATED, IN_REVIEW,
CHANGES_REQUIRED, APPROVED, PUBLISHED, ARCHIVED. No title, slug, order, source,
learningPathId, moduleId, score, options, rubric or other authored field is added.

### P1 - Approved string bounds and storage

Use JavaScript string length (UTF-16 code units), matching existing model length
checks. Trim the outer whitespace of prompt, answer and explanation; preserve
internal Markdown whitespace and formatting. Apply their length bounds after
trimming. Preserve starterCode exactly, including indentation, leading/trailing
whitespace and line endings; apply its bound to the original string. Require
trim().length > 0 for every non-null text value. Reject empty/whitespace-only text.
Numbers, Booleans, arrays, objects and boxed strings cannot become strings.

50,000 characters follows F021 Read Markdown's precedent and accommodates code
and explanations without unbounded documents. It is an owner-approved per-field
refinement, not an earlier documented practice limit. Four bounded text fields cap authored text at
200,000 code units; no arbitrary nested payload is accepted. Do not add a separate
byte-budget contract unless approved. Smaller bounds reduce payload size but may
unnecessarily truncate realistic exercises.

Store content as untrusted, inert data. Do not execute, fetch, interpret or render
it. Code-like strings, HTML-like teaching examples and URLs in prose are not
automatically executable and must not be rejected by keyword blacklists. Length
validation is not sanitization or editorial validation; future UI must escape
code and use restricted Markdown rendering.

### P2 - Approved absence, defaults and nulls

- Missing/undefined required fields fail except the explicit Mongoose defaults
  for _id, status, schemaVersion and managed timestamps/version metadata.
- Optional explanation, starterCode and language remain absent when omitted;
  no automatic empty string, null, language or answer is inserted.
- explanation rejects explicit null. starterCode and language preserve explicit
  null because Database Design lists null for these fields. Neither accepts an
  empty string as a substitute for absence.
- Required fields reject null. Enum strings must match exactly: no trimming,
  case conversion or numeric/string coercion. Version rejects '1', null, NaN,
  Infinity, fractions and any other number. No default question type/difficulty.
- Undefined optional properties represent absence; the model does not promise
  to distinguish an omitted property from a property supplied as undefined.

### P3 - Approved code/language applicability

The owner explicitly expanded starterCode to optional inert question-context code
for all four types. Preserve the documented field name; do not store solutions in
this question-context field or execute it. This supersedes the CODING-only proposal.

| Type | starterCode | language |
| --- | --- | --- |
| CODING / OUTPUT / DESCRIPTIVE / SCENARIO | Absent, null or bounded nonblank string | Absent/null when code absent/null; JAVASCRIPT or TYPESCRIPT required when code is a string; valid language may exist without starter code |

Questions without code need no language. A language may identify question context
without requiring a snippet. Both nullable fields retain documented null support.
Do not infer language from Technology, parse code or implement a compiler.
No new code field or language enum is added. Evaluation remains deferred.

### P4 - Approved strict identifiers and object inputs

Accept genuine Mongoose Types.ObjectId values or exact 24-hex strings, including
uppercase hex, converted to ObjectId. Reject arbitrary objects with toString,
numbers, buffers, 12-character strings, padded strings, trailing newlines, null
and arrays. Apply the same explicit-ID rule to _id and all five references.

Use strict: 'throw' and non-coercing scalar validation. Reuse F026's root input
inspection pattern where necessary to reject keys Mongoose otherwise ignores.
Construction accepts a plain data object (Object.prototype or null prototype),
or missing input followed by required-field validation. Reject other containers,
accessors, symbols, prototype-manipulation keys and unsupported root keys rather
than silently stripping them. Allow only the listed schema fields and internal
Mongoose metadata. Do not execute getters to inspect submitted values.

There are no authored nested-object/array fields. Reject evaluation, answer objects,
rubrics, arbitrary JSON/Map/Mixed fields and nested pseudo-IDs. Strict validation
does not establish foreign-key existence, matching ancestry, provenance ownership
or User ADMIN role/status. Future authorized services must independently check
parents, derive consistent denormalized IDs and authenticate/authorize authors.

### P5 - Approved lifecycle, metadata and validation boundary

Use timestamps: true, strict: 'throw', autoCreate: false, autoIndex: false and
bufferCommands: false. Importing the model must not connect, create a collection,
build indexes or alter records. Preserve Mongoose's internal __v convention.

Use DRAFT and schemaVersion 1 defaults following F021/F026. Adding schemaVersion
is an approved explicit refinement to the practice table, consistent with the
general versioning principle. No migration, reader coercion or automatic rewrite
of legacy data is included. A future changed version requires a separate contract.

Validate canonical status membership only; do not implement a transition graph,
publish operation or automatic promotion. Accepting PUBLISHED in a model test
does not grant publishing authority. createdBy/updatedBy stay caller-supplied
required references; timestamps do not prove an Admin performed the operation.

Normal saves generate createdAt/updatedAt using Mongoose. If timestamp values are
explicitly supplied for trusted persistence/hydration, accept valid
Date instances only, not date-string/number coercion. __v retains Mongoose's
internal behavior; it is not user-authored input or an authorization mechanism.
Do not add a custom timestamp lifecycle or rewrite Mongoose timestamp semantics.

Cross-field P3 validation must execute on whole-document asynchronous validate()
and validated save(), including changes to existing documents. Do not claim
validateSync(), query updates with runValidators, bulk/raw collection writes or
aggregation pipelines enforce whole-document invariants. No query-write interface
is added. Tests and future supported writers must use the validated document path.
Selecting hidden fields for trusted edits must not silently erase them when saving
a normally projected document; integration tests must cover this preservation.

### P6 - Approved projection details and defense-in-depth boundary

Set select: false on answer and explanation. Ordinary find/findOne/findById,
including lean results, must omit both. In isolated trusted tests,
select('+answer +explanation') can retrieve them unchanged. Test explicit normal
inclusion projections as well as default queries to establish actual behavior.

Do not claim this protects newly constructed/save-returned documents, explicit
field opt-ins, aggregations, raw driver reads or toObject()/toJSON() on a document
already containing answers. No serializer/redaction hook or DTO is introduced.
Future services must use allowlisted projections and DTOs, enforce attempt-based
answer authorization and avoid leaking answer-bearing data through logs/errors.
F030 exposes no public route and does not implement answer unlocking. Required
answer validation applies to new/full documents, not an invented requirement to
populate excluded answer fields on every unrelated edit.

### P7 - Approved implementation shape and documentation reconciliation

Use local helpers and existing model patterns within practice-question.model.ts;
do not extract shared infrastructure or modify other models. During the owner-
approved implementation gate, update Database Design to record P1-P6 as approved
refinements, and API Design to record no endpoint/authorization implementation.
The feature plan and roadmap transition to IN_PROGRESS under that approval.

## Indexes and deferred evaluation

Declare exactly the documented nonunique indexes:

- `{ conceptId: 1, status: 1, difficulty: 1 }`
- `{ technologyId: 1, type: 1, status: 1 }`

Retain MongoDB's normal unique _id index. No question-text uniqueness, additional
compound unique constraint, TTL, ordering or text-search index is proposed.
Duplicate question content is not prevented by these indexes. Explicit creation
of test indexes is allowed only during separately approved disposable integration;
normal startup must not create them.

The optional evaluation object is **explicitly deferred by owner decision**:
its nested contract is undefined. Do not declare it, accept arbitrary objects or
silently discard supplied evaluation. Unknown-field rejection applies. Database
Design must retain the future requirement with an explicit F030 deferral; do not
claim evaluation, grading, scoring, answer authorization or full PRD practice
acceptance is implemented. This is a known scoped refinement, not a hidden conflict.
